# 资产设计总控

用于用户明确提出的跨资产统一设计、关联检查与交付，或明确调用本入口的任务。只做单一领域时使用相应入口，不因读到其他资产而扩大范围。剧本标准化、场记和正式资产提取由独立剧本插件提供；本插件可分析原始剧本，但临时工作标识不得冒充正式资产 ID。

先读 [工作流](../../references/workflow.md)。第一次建立全剧理解、来源变化或理解矛盾时读 [全文理解](../../references/full-script-understanding.md)；派发前读 [交接与采用](../../references/domain-handoff.md)；涉及已批准资产、导入或版本变化时读 [审批与变更](../../references/approval-and-change.md)。具体数据以 [接口](../../references/interfaces.md) 和包内 schemas 为准。

## 先理解，再安排设计

1. 定位项目与授权范围，核对剧本、正式资产表及已有产物的版本。用内置 harness 初始化或恢复台账；原资料只读，运行产物放在项目目录。按源单元阅读全文或复用哈希一致的已读内容，跨单元综合冲突、转折、关系、时间与观众信息。记录真实阅读覆盖，不能用资产表摘要或脚本自动切块冒充阅读。
2. 建立可复用全剧上下文与项目美术基准。前者记录故事因果、世界条件、资产功能、跨域交互和来源；后者将时代技术、材料与工艺、色彩光线、形状和符号转成可执行规则，并标注事实、推导、创作选择与待确认。项目基准集中确认；不让所有人物、场景、道具共享同一颜色或贴同一图腾。
3. 全剧只做轻量资产关系与工作地图，当前授权批次才深化。保留原表 ID、状态和顺序；表外发现列候补。明确谁在何时使用什么、与哪处空间发生怎样的交互，以及哪些关系只是推测。把真正影响设计的约束写成任务，不把故事复述当成设计指令。
4. 依赖决定顺序。需要手持尺度的道具与人物身体、需要容纳道具的空间与实体体量等，可先形成共同设计约束，再分域细化；相互引用不一定形成硬阻塞。独立任务可并行，未确认的关键约束只暂停相关项。循环依赖先提交具体冲突和一套推荐取舍，不反复互派任务。

## 实际调用和整合

经包内临时执行器调用 [角色](../../bundled-plugins/character-assets/skills/character-assets/SKILL.md)、[场景](../../bundled-plugins/scene-assets/skills/sence-prompts/SKILL.md)、[道具](../../bundled-plugins/prop-assets/skills/prop-concept-design/SKILL.md)。向它们传递同源全文路径、相关理解、稳定 ID、当前状态、设计目标、已批准锚点、保持项、问题及所需交付；保持子插件根目录，按其相对路径加载实际 Skill 与知识。人物专属分析交角色子插件，场景设计遵循场景子插件准则，道具按其分阶段与选案规则工作。

使用 `plan`、`run` 与 `adopt` 记录真实任务、返回文件和采用决定；命令见工作流。内部执行使用隔离的临时会话，禁止为了派发而创建用户侧可见新聊天，禁止用“已调用”标签代替真实返回物。任务失败或等待资料时保留具体原因，独立项继续。一次运行不自动采用；总控查看文件、记录采用后，再运行依赖任务。只允许节点写自己的产物目录；子插件正式项目及已批准文件须在明确领域操作中更新。

整合时检查三类设计是否回应同一段故事、共享适用的世界规则、满足交互和尺度、保持身份与空间连续性，并具有具体可画结构。逐项写采用、部分采用或退回的原因和来源；一套连贯推荐优先，重要分歧才交备选。母插件的 `adopt` 只确认整合采用，不是用户对领域设计或图片的批准。

## 审批和交付

项目美术基准与跨域关键取舍由母插件集中提交用户；个人设计、场景阶段、道具选案与具体图片仍由相应子插件保留审批。提示词不等于成图，模型检查不等于用户确认，未实际查看的图不得记为审查通过。来源或基准改变后保留旧版，标记受影响的任务与资产复核。

默认交简洁的人物／空间／物件关系、当前推荐、关键依据、待确认项及实际文件位置。用 `index` 输出统一索引，保留各领域原始交付；状态区分已交文字、待选案、待回图、已批准和待复核。不要把“没有阻断”写成“整剧资产已完成”。已有角色项目只经显式导入，核对来源、稳定 ID 与文件哈希后保留可验证批准。母包与子插件来源见 [封装追溯](../../references/package-provenance.md)。
